# Plans

Use the smallest planning depth justified by risk. A plan coordinates work; it
is not automatically a permission gate. First determine the authorization
already present in the user's request, accepted project state, or explicitly
approved plan. If the user has already asked for implementation of a defined
scope, use planning to organize that work and continue through it. Do not ask
for a second approval merely because the work is large, multi-file, or written
down in `PLAN.md`.

For substantive work, a useful bounded loop is: brief → explore or structure →
build → targeted review when justified → integrated response → revise → verify →
meaningful state update. Do not force every phase on simple reversible work or
turn the loop into a controller. Reviewers diagnose; synthesis chooses one
coherent response; verification judges the result.

Preserve human ownership of genuinely new consequential choices: architecture
or public API direction, central claims, publication or release, deployment,
irreversible changes, security-sensitive behavior, and new dependencies unless
the user has explicitly delegated that choice. When findings interact, choose
one integrated response, state implementation order and global constraints, and
identify suggestions deliberately not adopted. Prefer a simple coherent revision
over locally optimal changes that sprawl.

A decision memo may state options, evidence, trade-offs, unresolved questions,
and the owner decision. If a consequential choice is still unresolved, stop at
that choice. Otherwise complete the authorized work without asking whether to
continue. A plan file records intent and coordination; file existence alone does
not prove authorization.
